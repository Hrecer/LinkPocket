# UiBench —— 大库综合性能评估台

UiBench 启动 LinkPocket 主窗口，在可见窗口的渲染路径下执行导航、搜索、排序与写操作等套件，
把耗时拆到 **引擎 / VM / 布局 / 渲染** 四段，并输出文本与 JSON 报告。

它不生成业务数据，也不修改传入的数据库文件：测量时把库复制到应用数据区再运行。

## 1. 前置条件

- Windows 桌面会话（需要真实窗口与屏幕渲染；离屏模式只用于对照）。
- 一个已完成初始化的 LinkPocket 数据库（当前 schema）。库的规模决定各项读数。
- `--folder` / `--deep-folder` 必须指向该库中真实存在的目录 ID；不传时使用内置示例 ID。
- `cold` 套件会清理系统文件缓存与 SQLite 连接池，需要提升权限的终端。

### 1.1 测试库准备

仓库内的 `tools/dev-seed` 生成纯合成测试数据（不访问外部站点、不下载图标）。
在仓库根目录运行：

```powershell
$env:LINKPOCKET_DB = "<隔离库路径>"
python tools/dev-seed/_seed_db.py          # 基线：目录 / 书签 / 回收站
python tools/dev-seed/_seed_100k.py        # 追加 10 万书签 + 100 层目录（匹配默认目录 ID）
python tools/dev-seed/_seed_explode.py     # 可选：10 万目录的复杂树
$env:LINKPOCKET_UI_BENCH_DB = "<同一个 10 万库>"
python tools/dev-seed/_seed_dedup_bench.py # 可选：查重场景库（从 10 万库复制）
```

测试库是运行产物，应放在源码目录之外；UiBench 只读取 `--db` 指定的库并复制到应用数据区。
更多脚本说明见 `tools/dev-seed/TOOL.md`。

## 2. 构建与运行

```powershell
cd <UiBench 目录>
dotnet build -c Release
dotnet run -c Release -- --db "<测试库路径>"
```

常用参数：

```text
--db <path>            测试库路径；工具会复制到应用数据区，源文件不动
--folder <id>          被测目录（示例默认值仅作占位）
--deep-folder <id>     深链套件的最深层目录
--rounds <n>           切页/刷新轮数（默认 6）
--only <suite,...>     只跑指定套件（逗号分隔）
--offscreen            离屏对照：不产生真实渲染帧，读数偏乐观
--noshadow             仅在测量进程内摘掉窗口外壳投影
--max                  以最大化窗口测量
--startup-wait <ms>    启动后等待一段时间再开始，并记录等待窗口内的 UI 停摆
```

不带 `--only` 时运行默认套件集合。

## 3. 产物

- `bin/<configuration>/net10.0-windows/ui_bench_report.txt`：逐条读数与门禁汇总。
- `bin/<configuration>/net10.0-windows/ui_bench_report.json`：结构化指标，便于脚本比较。
- `logs/*.jsonl`：应用日志，导航阶段耗时在 `cat=app.nav` 记录的 `ms` 字段中。

## 4. 指标定义

| 指标 | 含义 |
|---|---|
| `wall` | 动作 → 结果在屏幕上可见（导航类以首帧渲染为准；搜索类以首帧结果落地为准） |
| `stall` | UI 线程最长单次同步阻塞（动作本身的同步段也计入） |
| `layout` | 显式请求布局套件时，刷新收尾处的强制 `UpdateLayout()` 耗时 |
| `tail` | 首帧之后观察窗内 ≥32ms 的停顿（取最大与总和） |
| `rows` | 结果集行数 |
| `containers` | 已实例化的行根数量（虚拟化是否生效的直接判据） |

`wall` 与 `stall` 分开看：`wall` 回答“多久看到结果”，`stall` 回答“交互最长被卡住多久”。
`--offscreen` 不会产生真实渲染帧，只用于快速对照，不作为性能结论。

## 5. 套件

| 套件 | 内容 |
|---|---|
| `open` | 冷开目录、退回根、缓存命中重开 |
| `deep` | 上百层嵌套目录的打开与面包屑/树展开 |
| `switch` | 设置页 ↔ 浏览页反复切换 |
| `refresh` | 原地刷新 |
| `menu` | 行右键菜单（共享实例与逐行切换） |
| `dirty` | 批改 200 条后的刷新/重开 |
| `layout` | 布局分路 |
| `shift` | 导航后的布局位移取证 |
| `mutations` | 新建文件夹 / 新建链接 / 删除链接 / 删除文件夹的端到端延迟 |
| `search` | 搜索全链路：宽命中 / 窄命中 / 无命中 / 路径范围 / 范围切换 / 缓存重复 / F5 |
| `smartlist` | 智能列表四个预设的首开、全量落地、排序、F5 与末行可达 |
| `dedup` | 查重主表、明细分页、删除与恢复 |
| `sorts` | 浏览页与搜索页各列的表头排序（点击 → 新序上屏） |
| `folders` | 大规模目录树、文件夹搜索、目录快照与深树 |
| `cold` | 完整冷缓存：每项测量前清系统文件缓存与 SQLite 连接池（需要提升权限） |
| `searchproto` | 搜索加载模型原型：总数占位 + 后台原位填充，不接产品搜索 VM |

## 6. 判定与门禁

报告末尾汇总所有门禁，任一条失败进程退出码为 `2`。门禁分为三类：

- **首帧/首屏**：导航首帧、搜索首屏（完整行）、范围切换与 F5 的墙钟上限。
- **可达性**：结果总数、全量补齐、末行可达、补页期间拖到底与快速甩动的稳定性。
- **资源**：内存增量、行容器数量、结果集 extent 漂移。

读数取决于测试库规模、窗口尺寸与缓存状态。比较版本时应在相同库、相同窗口形态、
相同缓存状态下运行，并同时保留 `wall`、`stall` 与 `containers`。

## 7. 完整冷缓存套件

`cold` 套件在一次测量前清理：

1. SQLite 连接池与托管读缓冲；
2. 系统文件缓存工作集；
3. 系统待机列表（standby list）。

进程与界面保持热态，因此这是“数据冷、进程热”的测量。清理缓存需要提升权限；
未提升权限时套件会如实报告并跳过，不会用热缓存冒充冷缓存。

## 8. 注意事项

1. **STA 线程**：顶层 `Main` 不是 STA，UI 逻辑必须放在显式 STA 线程上。
2. **VM 从可视树取**：页面对象图是 Scoped，从根容器解析会拿到另一个实例，读到 `Rows=0`。
3. **虚拟化看两件事**：行容器数量与面板 `Extent/Viewport`；只看是否设置了 `SetIsVirtualizing` 会漏判。
4. **首屏包含首次布局**：模板虚拟化下设置 `ItemsSource` 只登记数据，行容器在紧接着的布局里实例化；
   测量终止条件必须包含首次布局。
5. **首帧与全量分开**：首帧量“完整行可见”，后台补全与末行可达单独计量，不混入首屏读数。
6. **补页期间的压力项**：拖到底/甩动必须从补全仍在进行时开始，并在 detail 中记录该状态。
7. **清理自己创建的数据**：写操作与查重套件结束时恢复现场，保证同一库可重复运行。
8. **测试库与产物分开存放**：数据库、图标缓存、日志与报告都是运行产物，不应与源码混放。
